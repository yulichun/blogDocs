# 结论：

优点：
1. 整个系统是开源的
2. 支持配置管理和监控主机和服务，但我们的业务不一定支持，因为他主要对接的云服务、k8s，还得实践下，判断是否可以运维普通主机
3. 监控采集支持各类探针插件，其实现了自己的时序数据监控，基于mongodb
4. 以主机为运维目标，对主机上的服务进行运维管理以及监控
5. 以业务为维护对象，比如可以在其建立国密系统业务、证券app业务、财务管理系统业务，针对各个业务运维管理
6. Web 可视化的业务拓扑，方便查看一个业务的监控情况

缺点：
1. 整个系统太大了，监控基于CMDB，CMDB基于蓝鲸 PaaS管控平台（类似ansible，但更大，支持云服务，支持k8s），依赖的中间件也不少

# 蓝鲸配置平台（BK-CMDB）

蓝鲸配置平台是一款面向应用的 CMDB，为应用提供了各种运维场景的配置数据服务。

## 大概的用法：

1. 创建业务：业务指的是项目，比如证券交易app业务，这个业务下会包含主机、网络设备。
2. 创建服务模型：服务模型（其核心应该是自定义配置模型CI），比如mysql、redis、kafka等各类应用的服务模型，目的是通过服务模型自动配置管理主机上的这类应用
3. 创建主机：主机就是主机服务器，或者是虚拟机，或者是云主机，服务模型会把应用下发到主机，主机内包含各类应用。
4. 创建网络设备：如路由器、交换机、防火墙等，应该只是维护一些信息，没有配置管理功能
5. 创建关联关系：把主机和服务模型关联，关联后服务模型会自动管理配置主机，在主机上安装服务；主机和业务关联；网络设备和业务关联；

在建立关联关系后，系统会自动生成一个业务的拓扑图，会把包含的网络设备、主机、应用关联起来，运维人员可以管理主机上应用的配置、看到监控情况。

## 特点及优势

1. 自定义配置模型（CI）管理：该功能是系统的核心，实现的是类似ansible的功能，但是可以通过界面自定义模型，管理配置流程
2. Web 可视化的业务拓扑
3. 全面的 API 服务
4. 自动发现和主机快照
5. 支持跨云管理
6. 动态查询分组
7. 对外开源

# 蓝鲸监控平台(BK-MONITOR)

生态闭环 依托蓝鲸 PaaS 深度整合了 CMDB，故障自愈，日志平台，作业平台，节点管理，数据平台，工单等能力，对CMDB、节点管理、权限中信、作业平台、用户中心是强依赖。实现了：
- 主机监控：硬件、操作系统的监控
- 进程监控：基于CMDB的一个探针实现了进程监控，类似process-exporter
- 拨测
- 应用监控
- 对接promethues exporter

## 大概用法：

监控平台是强依赖配置平台，基于CMDB，会基于CMDB维护的主机上配置一些采集策略，然后是配置告警策略、告警组等。

- 采集策略：配置如何采集主机上的监控数据
  - 默认策略：CMDB会默认安装硬件、操作系统和进程的采集器，是蓝鲸自己实现的采集器
  - 自定义采集配置：支持配置exporter、datadog、jmx等各类监控插件，应该是利用CMDB的功能实现了插件的管理
  - 脚本插件：脚本方式采集数据，脚本返回的数据需要符合一定的数据格式
  - 服务拨测
- 告警组、告警策略：配置要通知的人、组，以及如何告警、自定义告警信息格式
- 报表视图：类似grafana的图表功能，用的就是grafana
- 分析定位：通过数据检索可以做到指标检索、数据对比，对比不同维度的数据
